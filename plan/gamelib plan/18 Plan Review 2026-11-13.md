## 3. Architectural limitations found
Full table in [[02 Architecture#Limitations found in the review]]. In short:
1. A `games` row conflates **game + store licence + installation** → same game on two stores is two entries.
2. `Source` is a **closed enum** used in 13 files (even theme colours).
3. Providers, metadata and friends are **hard-wired**; no shared rate-limit/caching/API-key handling.
4. Playtime only works when the exe runs **inside the install folder** and the game was started from GameLib.
5. API keys in **plain text**.
6. Single crate (fine now, slower as egui grows; blocks sharing types with a future server).
7. Small reward exploits: unlimited idle playtime pays; delete + re-add lets "finished" pay twice ([[26 Progression and Stardust Economy#Weak spots in today's rewards (found in the code review)]]).

What's **good and kept**: UI/logic separation, worker threads + channels, pure tested decision functions, fixture-tested parsers, WAL + per-thread connections, transactional scans/purchases, forward-safe migrations.

## 5. The biggest decisions in this review
1. **Data model before features:** Phase 1 starts with the game/installation/ownership split ([[20 Game Identity and Installation Model]]), because mods, stats, profiles and discovery all depend on "one game = one row".
2. **Order changed:** a **local-first Discovery & Progression** phase moves before Identity; the backend waits until Phase 4 ([[28 Expanded Development Roadmap#Order and why it changed]]).
3. **Integrate, don't rebuild** for modding ([[22 Modding Architecture]]).
4. **Compiled-in providers, no plugin system yet; small workspace split** ([[21 Provider Architecture]]).
5. **Keep Rust + egui + SQLite** ([[24 Backend and Cloud Infrastructure#Technology review: what stays and why]]).

## 6. Main technical risks
| Risk | Phase | Mitigation |
|---|---|---|
| Live APIs/GOG behave differently from fixtures | 0 | M9 acceptance checks; regression tests |
| Schema v3 migration loses history | 1 | Keep game ids; automatic DB backup; migration tests on a copy of a real `library.db` |
| Wrong automatic merges | 1 | Only exact-ID auto-merge; review screen; undoable merges |
| EA / Xbox detection or tracking not feasible | 1 | Time-boxed spikes; folder scan fallback; extra watch paths |
| Provider terms (Nexus registration, IGDB commercial terms, Steam Web API terms) | 1–4 | Personal keys while personal; register/read terms before any public release; server-side proxies for secrets |
| Breaking game installs with mods | 2 | Deploy manifests, never delete untracked files, prefer hand-off to MO2/Vortex |
| Security/privacy mistakes once accounts exist | 4 | Use a proven auth service; private by default; tests for access rules |
| Moderation and legal duties (UK GDPR, Online Safety Act) | 4–5 | Moderation tools before UGC; read Ofcom guidance; adult owner |
| Scope creep for a solo developer | all | Every milestone ships; Phases 2–6 re-planned after Phase 1; explicit out-of-scope lists |
